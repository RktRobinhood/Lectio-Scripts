# Agent instructions — Lectio Scripts

This repo stores, versions, and updates Tampermonkey userscripts for Lectio (a Danish school timetable/messaging platform, `https://www.lectio.dk/lectio/*`). Users install scripts manually (copy-paste) or through the Lectio Manager. Domain vocabulary lives in [CONTEXT.md](./CONTEXT.md); architectural decisions live in [docs/adr/](./docs/adr/) — read both before making non-trivial changes.

## Non-negotiable invariants

- **No shared runtime code between modules.** Every `modules/*.user.js` file contains its own feature logic and must run safely if copy-pasted alone into Tampermonkey. Never introduce a shared library, common helper file, or shared CSS dependency between modules. Optional presentation registered with the Manager-owned dock is unavailable when the Manager is absent and must fail quietly rather than recreating fixed positioning; see [ADR-0012](./docs/adr/0012-manager-owned-shared-dock.md). See [ADR-0001](./docs/adr/0001-manager-module-separation.md).
- **No build step.** Plain userscripts only — no bundler, no `package.json`, no transpilation. Write code as it will run.
- **No server-side component.** `catalogue/modules.json` is static JSON fetched over HTTPS; nothing dynamic or executable lives server-side. See [ADR-0003](./docs/adr/0003-static-catalogue-independent-versioning.md).
- **The Manager never gains feature-specific logic.** `manager/Lectio-Manager.user.js` only discovers modules, links to install them, renders generic settings, and provides the generic shared dock described by [ADR-0012](./docs/adr/0012-manager-owned-shared-dock.md). If a request sounds like "have the Manager do X for module Y," the answer is to put X in module Y, not in the Manager. See [ADR-0001](./docs/adr/0001-manager-module-separation.md).
- **Persistent global controls use the Manager dock.** A module that needs an always-available button, toggle, badge, status, or flyout registers semantic data through the [dock event contract](./docs/manager-dock-api.md). It must not choose fixed viewport coordinates, z-index, shared icon dimensions, or flyout placement. Page-local UI that belongs beside page content may remain page-local. During incremental migration only, a pre-existing floating control may retain an explicit user-selectable legacy location for compatibility; its dock mode must use only the Manager-owned placement, and new persistent controls do not get this exception. The dock is the modules'; what the Manager may signal on its own behalf lives on its gear, in two shapes and two colours, and the default answer to a new badge is no — see [docs/manager-signals.md](./docs/manager-signals.md).
- **No memory leaks.** Modules run persistently on every matched Lectio page load. Any listener, `setInterval`/`setTimeout`, or `MutationObserver` a module adds must be capable of being torn down or scoped so it doesn't accumulate across navigations. Be conservative with polling.
- **Modules should be school-agnostic by default.** The project's goal is to work at any Lectio school, not just the maintainer's own — derive the school id from `location.pathname` (as Chairs Up does) rather than hardcoding one school into `@match` or into scraping logic. See [ADR-0007](./docs/adr/0007-school-agnostic-by-default.md).
- **New modules must expose their key colors as `--lectio-theme-*` CSS custom properties**, each with the module's own current hard-coded value as its `var()` fallback (e.g. `background: var(--lectio-theme-accent, #0f6f6f)`), so [Lectio Theming](./modules/Lectio-Theming.user.js) can recolor them automatically if installed, and the module looks visually unchanged if it isn't. See [ADR-0006](./docs/adr/0006-css-custom-property-theming-seam.md) for the exact variable names and semantics. This is required for new modules, not optional.
- **One owner per lesson block.** A module that colours `.s2skemabrik` claims the *surface* by writing the colour inline; [Lectio Theming](./modules/Lectio-Theming.user.js) keeps the frame (border, radius, shadow) and stands aside from any block carrying an inline background, including one painted by a third-party extension such as Lectio Farver. Never re-acquire a block's surface from a stylesheet rule, and never strip inline colour a module did not write itself. See [ADR-0011](./docs/adr/0011-lesson-block-colour-ownership.md).
- **Scripts stay human-in-the-loop — no automating consequential Lectio actions.** A module may make something *easier* (surface information, pre-fill a form, deep-link to the right page) but must never submit, cancel, register, or otherwise write consequential state (attendance/fravær, lesson cancellations, feedback, messages, grades) without an explicit click from the person it affects, in that moment. No background/scheduled automation of any of this. See [ADR-0009](./docs/adr/0009-human-in-the-loop-no-automated-consequential-actions.md).
- **No features that enable academic dishonesty or misrepresentation.** Never build something whose purpose is to fabricate a record or substitute automation for a person's own honest input — e.g. auto-writing a fravær excuse or auto-completing elevfeedback. If a feature idea would let someone present something as their own genuine input when it wasn't, it doesn't belong in this project, however it's framed. See [ADR-0010](./docs/adr/0010-no-academic-dishonesty-features.md).

## Contribution model

Solo-maintained by the repo owner with AI agents as the primary collaborators. **Issues only — no external pull requests are merged** (see [ADR-0004](./docs/adr/0004-issues-only-no-external-prs.md)): userscripts run with broad access inside an authenticated Lectio session, so outside code is a supply-chain risk the owner won't accept. Feature/bug feedback from end users (non-technical teachers and students) arrives via GitHub Issues, linked from the Manager's footer. The user-facing statement of this is [CONTRIBUTING.md](./CONTRIBUTING.md) and the README's *Issues, not pull requests* section; the enforcement is [`.github/workflows/decline-pull-requests.yml`](./.github/workflows/decline-pull-requests.yml), which comments the reason on any pull request not opened by the owner and closes it. GitHub offers no switch that turns pull requests off on a public repository, and forking cannot be disabled on one, so that workflow **is** the off switch — do not quietly break it, and never add a checkout step to it (it runs on `pull_request_target`, so checking out the pull request's own code would hand a stranger a write token).

Every completed repository change must be committed and pushed to GitHub **on `main`**; work is not finished while relevant changes exist only in a local worktree or an unmerged branch. Before ending a session, confirm with `git fetch` that the actual changed files are visible on `origin/main`, not just in a local branch's `git log` — a stale local clone that was never fetched can look identical to a branch that never made it to `main`, so check the remote, not just local history.

**Every module change ships to Unstable first. Stable is promoted by hand, on the owner's word.** This is the release path for every userscript that is not the Manager, and it is not optional — see [ADR-0014](./docs/adr/0014-unstable-first-releases.md).

- **Unstable is a folder, not a Git branch.** `modules-unstable/` and `modules-unstable/modules.json`, both on `main`. Nothing about branching changes; "push to `main` when it's done" still holds for unstable work.
- **Working on a module means working in `modules-unstable/`.** If the module is not there yet, copy it in, bump its version, point its `@updateURL`/`@downloadURL` at `modules-unstable/`, and add its entry to `modules-unstable/modules.json` with the same `id` as the stable entry — the overlay replaces a stable entry with a matching `id`, so testers get the copy and everyone else keeps the shipped one.
- **While a module is under test its copy in `modules/` is frozen.** Do not edit it, not even for a one-word fix. There is no merging at promotion time; promotion is a copy.
- **One number line, no suffixes.** Stable at `1.9.3` → first unstable change is `1.9.4`, further rounds `1.9.5`, `1.9.6`, and promotion bumps once more to `1.9.7` for Stable. Stable skipping numbers is correct. The promotion bump is what pulls testers off the unstable file before it is deleted; skipping it strands them on a dead `@updateURL`. Pre-release suffixes (`-beta.1`) are still banned by [ADR-0003](./docs/adr/0003-static-catalogue-independent-versioning.md).
- **Promote only when the owner says to promote**, in those words. The six steps are in [ADR-0014](./docs/adr/0014-unstable-first-releases.md#promoting); do them in one commit.
- **The Manager is exempt** and goes straight to Stable, because it is what delivers the channels — a Manager that cannot boot cannot be switched away from. Its protection is the test suite.
- **One exception, narrow:** a fix for something already broken for stable users (a module throwing on load, dead against a Lectio change, losing data) may go straight to Stable. Name the break in the commit message. "Would be nice sooner" is not an exception, and a feature riding along with a fix is not one either.

**A version bump is never one edit — run `node scripts/check-versions.mjs` before you call a change finished.** Touching a module's behaviour without moving *every* number that describes it produces one silent symptom: the Manager keeps offering the old version, so nobody is ever told an update exists. The change looks delivered and is invisible. This has now cost several rounds of "why am I not seeing the update", which is why it is a script and not a habit. Three places must agree, and a fourth rule has no file of its own:

| What | Where | Why it matters |
| --- | --- | --- |
| `@version` header | the `.user.js` itself | what Tampermonkey compares for its own update check |
| Registration version | `MODULE_VERSION` or the frozen `MODULE` object's `version:` | what the module reports at Discovery, and what the Manager compares against the catalogue to decide "Update available" |
| Catalogue version | `catalogue/modules.json`, or `modules-unstable/modules.json` for an unstable module | the number users are actually offered; the Manager reads this over HTTPS, not the file on disk |
| The bump itself | — | if the file changed at all, the number must move: three-part `MAJOR.MINOR.PATCH`, exactly one part per change, never reused and never decreased (see [ADR-0003](./docs/adr/0003-static-catalogue-independent-versioning.md) for which part to bump) |

The Manager has a fifth: `catalogue/modules.json` carries a `manager` entry, and the self-update notice compares it against the `MANAGER_VERSION` constant. A stale entry there fails silently — the notice simply never appears and the Manager goes on looking current. That entry takes the same optional `changelog` (and `i18n.da.changelog`) as a module entry, shown on the self-update notice under the version line, and the paragraph below applies to it too.

**Move the number, write the line.** A catalogue entry may carry an optional `changelog` — one or two plain sentences, in the reader's terms, about what *this* version changes for them — and the Manager shows it under the update row when it offers that version. Update it in the same edit as the `version` it describes, in whichever catalogue the bump lands in, and translate it in the entry's `i18n` block alongside `name` and `description` if you can; an untranslated one shows in English, which is what already happens to a description. A stale changelog is worse than none, because it describes a version the reader is not being offered. Leaving it out is allowed and renders nothing at all — what is not allowed is leaving yesterday's line in place.

`scripts/check-versions.mjs` checks all of them and exits non-zero on any mismatch. It diffs against `origin/main` by default, so it also catches the case the other three cannot: a file edited with its version left alone. The Manager itself is exempt from the middle two rows — it never registers itself and is in no catalogue, so Tampermonkey's update check is the only thing that ships it.

**New module-scope state in any userscript goes *above* the boot block — run `node scripts/check-boot-order.mjs` too.** This is the sibling of the version-bump ritual above: one edit that reads as harmless, one silent symptom, and three shipped Manager versions already lost to it (1.21.0, 1.25.0 / issue #32, 1.27.0 / issue #30), plus two module near misses caught by hand (Chairs Up in #36, Unread in #24). Tampermonkey injects every script at `@run-at document-idle`, so `document.readyState` is never `'loading'` on a real install and `init()` runs **during the file's own top-level evaluation**. A module-scope `const`, `let` or `class` declared *below* that boot call site is therefore still in its temporal dead zone when `init()` reads it: the `ReferenceError` lands in one of the Manager's many `catch` blocks — a dozen of which are deliberately silent — and the Manager runs on degraded with nothing on the console. Symptoms shipped so far: nothing built at all; the cached catalogue discarded and both catalogues refetched from GitHub on every page load; the user's real dock replaced by the default and overwritten on their next save. `node --check` passes it, and so did CI and the full local suite, all three times. If the constant belongs beside the function that uses it, put it *inside* that function — a function declaration hoists and its body is not evaluated until it is called. Two guards now cover it, and they catch different things: `scripts/check-boot-order.mjs` finds the declaration in under a second in every `.user.js` under `manager/`, `modules/`, `modules-unstable/` and `templates/` (its header says how it finds each file's boot anchor, what the `// boot-order: not-checked — <reason>` marker is for, and why three current findings are listed as deferred to issue #58 rather than fixed in place), and `tests/fixtures/manager-boot-integrity.html` boots the Manager the way Tampermonkey does with every subsystem's stored state present and fails on any exception at all — including one that is caught and merely warned about, and one that is caught silently, which only the end state can see.

**The Catalogue is a public contract with Managers you no longer control.** Users install the Manager once and update it through Tampermonkey, whose update check is off by default, so old versions stay in the wild indefinitely. There is no server to roll back and no way to reach those installs: a Catalogue an old Manager cannot parse empties the module list for everyone still on it, silently and all at once.

Changes must be **additive**. Adding a key is safe — every shipped `validateCatalogue` copies named fields into a fresh object, so a key it has never heard of is ignored by construction. What breaks an old Manager is removing or renaming a field it requires (`id`, `name`, `description`, `version`, `installUrl`), changing `schemaVersion`, or making `modules` anything other than a non-empty array. `tests/catalogue-compat.browser.test.js` runs **every Manager version ever published** against the Catalogue as it currently stands and fails if any of them stops listing a module; both of those breakages were confirmed to fail it. Add a row to `SHIPPED_MANAGERS` whenever a Manager version reaches `origin/main`, and never remove one — removing the row does not remove that version from anyone's browser.

**Adding or renaming a module includes the issue templates.** The "which script" dropdowns in [`.github/ISSUE_TEMPLATE/`](./.github/ISSUE_TEMPLATE/) (`bug-report.yml`, `feature-maker-idea.yml`, `school-compatibility.yml`) list the modules by the name the Catalogue and the Manager show; they are the only channel non-technical users have (`blank_issues_enabled: false`), so a module missing from them is a report that arrives as "Other" and routes nowhere. Update all three in the same change that adds or renames the module — this drifted once already (issue #25), by four modules.

**Language lives in one file, never in a parallel copy.** A script carries both languages inline; there is no `-EN` / `-DA` pair to keep in step, and no language pack fetched at runtime (six of the eight modules run `@grant none` and cannot fetch anything). Measured: Danish costs 4.8 KB on the Manager's 197 KB. See [ADR-0013](./docs/adr/0013-one-script-per-module-both-languages-inline.md). The Manager owns the choice and publishes it on `<html data-lectio-language>` plus a `lectio-manager:language` event; a module reads that attribute, then `documentElement.lang`, then falls back to Danish — Lectio is Danish, so a module on its own stays Danish, while the Manager starts in English because it is mainly for IB students. Translating a module is optional; one that has not been translated is not broken.

**Dock icons are generated, not drawn.** They come from Lucide SVGs in [`assets/icons/`](./assets/icons/) and are inlined into the Manager by `scripts/build-dock-icons.mjs`, because a userscript is one file with no bundler and no runtime fetch. Run `node scripts/build-dock-icons.mjs --check` alongside the version check; never hand-edit the strings between the `BEGIN/END GENERATED ICONS` markers. Hand-drawing is what produced a palette with hollow rings for paint and a refresh arrow whose lower arc had its large-arc flag set, so it swept past 180° and swallowed the upper one. The set is monochrome on purpose: it inherits `currentColor`, so the dock recolours with the active theme instead of sitting on top of it.

**CI runs these gates, and does not excuse you from running them.** [`.github/workflows/checks.yml`](./.github/workflows/checks.yml) runs on every push and pull request to `main`: `node --check` over every `.user.js` in `manager/`, `modules/` and `modules-unstable/`, then `node scripts/check-versions.mjs` (checked out with full history, so its `origin/main` drift check is real), then `node scripts/build-dock-icons.mjs --check`, then `node scripts/check-boot-order.mjs`, then `node scripts/check-i18n.mjs` (the Manager's `en` and `da` string tables name the same keys, and so do the two sides of every module's marked `labels()` pair — `// i18n:en` / `// i18n:da` / `// i18n:end` around the two literals, the convention the skeleton shows; `t()` falls back to English silently and a module hands the Manager `undefined`, so a key missing on one side shows a Danish reader English, or a bare key, with nothing to say so), then the browser suite against the runner's headless Chrome via `CHROME_PATH`. Any one of them failing fails the job. But a push to `main` is what CI sees, so by the time it goes red the broken file is already on `main` and — for a catalogue or module change — already reachable by users; and a drift check on a push to `main` is comparing the pushed commit against itself, which is exactly the case it cannot catch. Run all five locally before you call a change finished. The workflow is the backstop, not the check.

**The browser suite launches Chrome through one helper, and cleans up after itself through the same one.** Every Chrome the suite launches gets a directory the harness owns: [`tests/chrome-harness.js`](./tests/chrome-harness.js) creates it, hands it to Chrome as both `--user-data-dir` and `TEMP`/`TMP`/`TMPDIR`, and deletes it in a `finally` so it goes on failure and on timeout too. Copy that shape in a new browser test rather than calling `mkdtemp` yourself — a profile alone is not enough, because Chrome unpacks component extensions and drops loose `.tmp` files in whatever temp directory it inherits, and that is what filled the maintainer's system drive (issue #43). Spawn Chrome with the harness's `runChrome` rather than your own `execFile`: it carries a wall-clock ceiling per launch and kills the process tree when it is reached, because a headless Chrome can print its DOM in full and then simply never exit, and an unguarded launch turns that into a twenty-minute CI timeout that reads like a broken change (issue #51). It fails as `CHROME_DID_NOT_EXIT` instead; `tests/chrome-watchdog.browser.test.js` holds the guard honest against a fixture that hangs on purpose.

**A correct bump still will not appear immediately.** The Manager caches the stable catalogue for **24 hours** (`STABLE_REFRESH_INTERVAL_MS`) and the unstable overlay for 5 minutes, and a page load only refetches a stale one (`refreshCatalogue({ force: false })`). So a freshly pushed *stable* module can be entirely correct and still show nothing for a day. The refresh button in the Manager header forces a refetch — say so when reporting a shipped bump, rather than treating "I don't see it" as evidence the bump is missing.

**Pushing from a worktree does not update the primary checkout's local `main`.** This has caused real confusion (2026-09-17, issue #19's shape-marker commit): the version bump was correctly on `origin/main` the whole time, but the primary checkout's local `main` branch was left several commits behind, because `git push origin HEAD:main` from inside `.claude/worktrees/<name>` only moves the remote ref, not the primary checkout's branch pointer. The repo owner looks at files in the primary checkout, not at `origin/main` directly, so a stale local `main` reads as "the change wasn't made" even when it was. After pushing from a worktree, also fast-forward the primary checkout (`git merge --ff-only origin/main`, run from the primary checkout, not the worktree) as part of the same finishing step, and verify by re-reading the changed file from there — not just by confirming the push succeeded.

**Closing issues is not optional.** When a commit lands on `main` that resolves a GitHub issue, close that issue as part of the same delivery, using a GitHub closing keyword in the commit message footer (`Fixes #N`, `Closes #N`, or `Resolves #N` — a bare `(#N)` reference does *not* auto-close). This has slipped before (issue #9's audit-fix commit landed real fixes but used neither a closing keyword nor a comment noting what was still open). If a commit only partially resolves an issue, say so explicitly in the commit body or a manual issue comment instead of leaving it silently open with no note — and if it fully resolves the issue, close it. Before finishing any task that references an existing issue number, check whether that issue should now be closed.

**Only work an issue that carries the `ready for agent` label.** The repo owner uses this label to gate which open issues are triaged and scoped enough for an agent to act on autonomously; an issue without it (including `[Idea]`-prefixed issues with open design questions still listed in the body) should be left alone — do not start implementation, just note the gap if asked. Remove the label, or ask the owner, if a labeled issue turns out to need a design decision only they can make.

Tampermonkey itself (not a custom browser extension) is the deliberately chosen distribution platform for now — see [ADR-0005](./docs/adr/0005-tampermonkey-as-platform.md) if you're tempted to suggest otherwise.

## Adding a new module

**Start from [`templates/Lectio-Module-Skeleton.user.js`](./templates/Lectio-Module-Skeleton.user.js)** rather than reproducing the boilerplate below by hand. It is a complete, working, do-nothing module — Discovery on load and on request, one setting of every control type the Manager renders, the theming seam, both languages, an optional dock item that fails quietly, and clean teardown — that you copy, rename, and cut down. It is a starting point, not a dependency: nothing imports it, it is in neither catalogue, and a module built from it is fully self-contained. [`templates/README.md`](./templates/README.md) carries the checklist for the two things a skeleton cannot enforce, the Experimental-first release path and the four places a version number lives.

A new module starts in Unstable like every other module change ([ADR-0014](./docs/adr/0014-unstable-first-releases.md)), so read `modules-unstable/` for `modules/` and `modules-unstable/modules.json` for `catalogue/modules.json` below until the owner promotes it. A new module is just:

1. A new `modules-unstable/<Name>.user.js` file with a standard header (`@name`, `@version`, `@match https://www.lectio.dk/lectio/*` or a narrower path, `@updateURL`/`@downloadURL` pointing at its own raw GitHub path — the one in the folder it actually lives in) that, on load and on receiving the `lectio-manager:discover` event, dispatches `lectio-module:register` with `{ id, name, version, settingsSchema, currentValues }` (an empty `settingsSchema: []` is fine if the module has no configurable options yet).
2. A matching entry in `modules-unstable/modules.json` (`id`, `name`, `description`, `category`, `audience`, `status`, `version`, `installUrl` under `raw.githubusercontent.com/RktRobinhood/Lectio-Scripts/`, `supportUrl`), moving to `catalogue/modules.json` on promotion.
3. Any color the module's own UI hard-codes (backgrounds, text, borders, accents) written as `var(--lectio-theme-name, <the module's own hard-coded value>)` per [ADR-0006](./docs/adr/0006-css-custom-property-theming-seam.md) — required, not optional, for new modules.

Nothing else is required, and the Manager's own code never needs to change for a new module. A module may additionally register an optional persistent control through the documented dock event contract; its feature logic remains in the module and must not throw when the Manager is absent.

**A new module cannot be exercised through the Manager until its Catalogue entry is on `main`.** The Manager fetches `catalogue/modules.json` from `main` and renders a module's settings only where it finds both a Catalogue entry and a live Registration, so a module installed from a branch registers correctly and still shows no settings panel at all — every control it offers is invisible, which looks exactly like a broken module. To exercise one before merging, point the `CATALOGUE_URL` in your own installed copy of the Manager at the branch; do not add the entry to `main` ahead of the module, or the Catalogue advertises an `installUrl` that 404s.

## Lectio platform notes (extracted from the existing modules)

- **School scoping**: a Lectio installation is identified by a numeric id in the URL path, e.g. `/lectio/223/...`. Every module derives it the same way — `location.pathname.match(/^\/lectio\/(\d+)\//)` — rather than baking a school into `@match` or into scraping logic, and no module hardcodes a school id anywhere. Unread Message Notifications was the last one to be generalized (it once shipped with `@match https://www.lectio.dk/lectio/223/*`); it now matches `https://www.lectio.dk/lectio/*` like the rest. What remains is verification, not code: its unread-detection selectors have still only ever been confirmed against school 223's actual rendering. See [ADR-0007](./docs/adr/0007-school-agnostic-by-default.md).
- **Timetable lesson elements**: lessons/bookings render as `a.s2skemabrik.s2brik[data-tooltip]`; the tooltip text carries the actual date/time (`D/M-YYYY HH:MM til HH:MM`, Danish) and room list (`Lokale(r): ...`). The `s2brik` class is not universal — an activity front page renders the same lesson as `a.s2skemabrik.s2normal` — and `.s2skemabrik` on its own is not a lesson at all: Lectio also hangs it on decoration, such as the `div.prepend-fonticon-activity.s2skemabrik` in an activity page's table-of-contents list. **Match a lesson block on `[data-tooltip]`, never on the class alone**, or decoration gets styled and scraped alongside the real thing.
- **Hold (class) identity**: a lesson block contains `<span data-lectiocontextcard="HE<digits>">` for each hold it belongs to — the stable identity — with the hold's display name as the span's text; the tooltip repeats the names on a `Hold: a, b` line (Danish). Teachers appear the same way with a `T<digits>` card. An activity with no hold at all (assembly, meeting, trip) is the reliable signal that it is not a class, which is what Subject Colours classifies on.
- **Your own timetable by week**: `/lectio/<school>/SkemaNy.aspx?week=<WWYYYY>&nosubnav=1` renders your own schedule for one ISO week, zero-padded week followed by the four-digit year (`052026`, not `52026`). Schedule cells carry `data-date="YYYY-MM-DD"`, and a full-week render has a `tr.s2dayHeader`.
- **Cancelled activities**: detected via the `s2cancelled` CSS class (on the element or a child) or tooltip text starting with `Aflyst!` (Danish) / `Cancelled`/`Canceled` (English fallback). Always filter these out rather than treating them as real bookings.
- **Room identifiers**: Lectio room ids appear in URLs/attributes as `RO<digits>` or bare numeric ids behind `type=lokale`. There's no direct API for "all rooms" — Chairs Up discovers them by harvesting room links off pages that happen to expose them (a room's own timetable page, the schedule front page, or an activity-edit page), then caches the result for ~30 days.
- **Unread messages**: found by locating nav text matching `/^(Beskeder|Messages)$/i`, then parsing a `"N unread"` pattern near it on the Forside (front page), with a fallback scan of message rows for `tr.unread`, `.message-list-thread-container.unread`, or `data-status="unread"`/`data-state="unread"` attributes. A parsing failure must never be treated as "zero unread" — that's a deliberate rule in the existing code, not an oversight.
- **English Mode** runs on every Lectio page (`@match https://www.lectio.dk/lectio/*`, no school restriction), uses a `MutationObserver` to catch newly-rendered Danish text, and falls back to the Google Translate API (`translate.googleapis.com`, `translate.google.com`) for text it doesn't recognize itself.
- Server-rendered pages can be fetched and parsed directly (`fetch(url, { credentials: 'include' })` + `DOMParser`) to read data the current page doesn't expose — used by Chairs Up to look up room schedules the visible timetable doesn't show.

## Visual starting point (current, informal — see also ADR-0006)

No shared stylesheet exists or should exist, but for visual consistency when hand-matching a new module's look:

- **Manager**: teal `#0f6f6f` (header background, buttons, active nav items), white panel `#ffffff`, body text `#10201e`, secondary text `#5e6870`, `Roboto, Arial, sans-serif`, 10px card/panel border-radius, thin `#d6dde0`/`#eef1f2` borders, minimal-stroke line-art SVG icons (gear, wrench, refresh, close, chevron). Its panel now reads the `--lectio-theme-*` seam (ADR-0006) with these as fallbacks.
- **Chairs Up**: alert-red gradient `#ff3155` → `#d9002f` for its badge/notice (deliberately urgent, not matched to the Manager's teal — a semantic-urgency color like this is a reasonable exception to the theming seam, same as Lectio Theming's own error/success colors).
- **Unread Message Notifications**: light blue `#cae6ff` badge background, dark navy `#001e2f` text.
- **English Mode**: mid blue `#35658c` accents, also migrated onto the `--lectio-theme-*` seam.

There is no enforced visual-*style* consistency (a new module can still pick its own accent color, as Chairs Up did deliberately for urgency), but every module's colors **must** go through the `--lectio-theme-*` seam from ADR-0006 with the module's own palette as the `var()` fallback — that's what lets [Lectio Theming](./modules/Lectio-Theming.user.js) recolor it automatically without either module depending on the other.

## Known gaps / future directions (not committed work, just notes)

- **The Manager's settings seam is active and section-aware.** `manager/Lectio-Manager.user.js` renders generic toggle/select/range/text/color/button controls from each module's `settingsSchema`, wired through the `lectio-manager:set-setting` event. A `color` control renders a native colour input and reports `#rrggbb` back; like every other type it carries no knowledge of what the module does with the value. A Manager that predates a control type skips that row rather than failing, so a module adding one should keep working either way. Controls may carry an optional `section` label for grouping in the focused settings view. A control may carry `audience: ['teacher']` (or `['student']`); on the Stable channel the Manager hides it from an account of the other type, which it detects from the page (issue #78), and on Experimental it shows everything. That is presentation only — the module remains the authority on what it does for each account type and must not rely on a hidden control being unset. A select may set `previewOnHover: true`; the Manager then emits `lectio-manager:preview-setting` while an option is hovered/focused and `lectio-manager:clear-setting-preview` when the temporary preview ends. The owning module must apply previews without persisting them. The Manager must continue to render older flat schemas without module-specific logic.
- **The Manager can measure browser storage, and knows nothing about what is in it.** `localStorage` for `lectio.dk` is roughly 5 MB shared by every module, and a module that cannot write catches the failure and carries on in memory — which is correct, and is why running out shows up only as settings that quietly stop sticking. The Manager's Storage section enumerates that origin's `localStorage` and sizes it, which is generic measurement any page could do. Everything else — whose a key is, whether it is a cache or the only copy of a learned palette, whether clearing it is survivable — arrives as a *Storage Declaration* on the module's Registration and is rendered as given. There is no table of keys in the Manager, it never parses or shows a stored **value**, and it never calls `removeItem`: a Clear button dispatches `lectio-manager:prune-storage` and the owning module does the deleting, with no fallback if nothing answers. A key no running module claims is listed as unclaimed and has no Clear button. `GM_*` storage is per-script and cannot be enumerated from another userscript, so a module holding it (English Mode is the only one) declares `area: 'script'` and the readout says it sits outside the page's budget rather than under-reporting by omission. The contract is [`docs/manager-storage-api.md`](./docs/manager-storage-api.md); a module is still responsible for expiring its own caches **on load**, because a bound that only runs on the path that happens to read the cache mostly does not run.
- **The Manager can carry a person's settings out and back in, and understands none of them.** The Backup and sharing section writes the values each module reported at Registration — only the keys its own Settings Schema declares a control for — plus the Manager's own preferences, as a versioned JSON file, and reads one back by replaying accepted values through the existing `lectio-manager:set-setting`. No module needed new code for it. A file is shown before it is saved and described before it is applied; an imported one is untrusted input, checked field by field against the *live* schema, so a module that is not running, a control that has gone and a value of the wrong type are skipped rather than guessed at. A learned cache, the problem log and Theming's background picture cannot travel in one, and the section says so. The format is [`docs/manager-settings-file.md`](./docs/manager-settings-file.md).
- **The Manager hands out turns for background work, and knows nothing about the work.** Four modules fetch Lectio pages in the background, each damping its own rhythm (timeout, `pagehide` abort, backoff, start jitter) — but nothing staggered them against each other, so a browser with several installed fired a burst at the school's server every poll interval, and no module could fix that alone because a module may not know the others exist. A module now asks the Manager for a *Request Slot* before background work and the Manager grants one at a time. Both fields on every event are opaque strings it compares and echoes; it never learns what is being fetched or why. **It fails open, and that is the property to protect:** the module's own clock is the authority, so no Manager, an old Manager that has never heard of slots, and a Manager that has stopped answering are one case costing one short pause — once per page view, not once per request, because a module remembers that nothing answered and any answer clears that again — and nothing the Manager sends can make a module wait longer than the module decided to. On the Manager's side the same rule holds twice — a full queue grants rather than refuses, and a slot nobody hands back comes back on a lease. Each module carries its own copy of the asking code; there is no shared runtime code between modules and there is not going to be. A slot reclaimed on its lease goes to the problem log, because a module whose background work keeps hanging is exactly what that log is for. The contract is [`docs/manager-request-slots.md`](./docs/manager-request-slots.md).
- **Resilience to Lectio's own changes.** Lectio can change its page structure at any time, and there's no automated monitoring for that today. The working principle: modules should feature-detect and degrade gracefully (as the "never treat a parse failure as zero unread" rule already does) rather than hard-depend on fragile selectors, and checking real Lectio pages for structural drift is a periodic manual/agent-assisted maintenance task, not an automated one yet. What now exists is the reporting half: a module tells the Manager that a selector it depends on matched nothing by firing `lectio-module:report`, and the Manager keeps a small redacted log of those signals and of the errors it catches, which a user can copy as one block into a bug report. The contract, and the reason a module may send a token but never a sentence, is [`docs/manager-problem-log.md`](./docs/manager-problem-log.md).
- **Unread Message Notifications is school-agnostic by construction, and unverified in practice.** ADR-0007's first test is half done: the `@match` was widened and the school id now comes from the path, so the module runs everywhere and the Catalogue advertises it that way. Nothing has confirmed its unread-detection selectors against a second school's actual rendering, and its own rule — never treat a parse failure as zero unread — means a mismatch shows up as silence rather than a wrong number, which nobody would report. Verifying it against another school is a diagnostic worth doing, not a known break.
- **Subject colouring is built and deliberately unfinished.** [Subject Colours](./modules/Lectio-Subject-Colours.user.js) learns your holds from your own timetable, colours the regular ones from the `--lectio-theme-*` seam, keeps one-off activities in a separate muted band, and shows a collapsed-by-default on-page colour key for whichever classes are currently on screen. Class hues are picked by a greedy search over OKLab perceptual distance under simulated protanopia/deuteranopia/tritanopia, not raw hue spacing, so two classes that would look identical to someone with a colour-vision deficiency get pushed apart (`tests/subject-colours-palette.browser.test.js` verifies this for 2–12 classes across a light and a dark theme). Known next steps are filed as their own issues rather than carried here: per-activity control over what counts as a class, and a non-colour channel (pattern/edge-style) per class for people who need one even under full colour blindness.
- **The central theme layer from ADR-0006 is now built**: [Lectio Theming](./modules/Lectio-Theming.user.js), with 44 named color schemes plus a custom palette whose four key colours can be imported from an image/website or picked by hand, and an optional background picture chosen from the user's own device (re-encoded and kept in that browser's `localStorage` only — it is never uploaded, and the module has no code path that would send it anywhere). Remaining work here is retrofitting the `--lectio-theme-*` seam onto Chairs Up and Unread Message Notifications (Manager and English Mode are done), continuing to verify Lectio's own unthemed surfaces against real saved pages (see the project's sample-pages memory) as new page types turn up gaps, and — the natural next step from issue #4 — named custom presets with theme export/import.
