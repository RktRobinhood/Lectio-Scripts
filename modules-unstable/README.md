# modules-unstable

**Where every module change lands first.** Not a Git branch — a folder and a catalogue, both on `main`, read only by people who have switched their own Lectio Manager to the release channel it serves — labelled **Experimental** in the Manager, since that is what it means to the students and teachers choosing it; `unstable` everywhere in the code, the stored setting and this folder. Stable users never see any of it. The rule and its reasoning are [ADR-0014](../docs/adr/0014-unstable-first-releases.md); the short version lives in [AGENTS.md](../AGENTS.md).

`modules-unstable/modules.json` is an overlay, not a replacement: an entry here with the same `id` as one in `catalogue/modules.json` replaces it for Unstable users, and an `id` that appears only here is an Unstable-only module. The Manager caches this overlay for five minutes against twenty-four hours for the stable catalogue, so a change here is visible almost immediately.

## Working here

A module being worked on exists twice — the frozen copy stable users have in `modules/`, and the live one here, at least one version ahead. While it is under test the copy in `modules/` is not edited for any reason.

Starting work on a module that is not here yet:

1. Copy it in from `modules/`.
2. Bump its version — `@version` and the version it registers, together. No `-beta` suffixes: plain `MAJOR.MINOR.PATCH`, as [ADR-0003](../docs/adr/0003-static-catalogue-independent-versioning.md) requires of every script in this repository.
3. Point `@updateURL` and `@downloadURL` at this folder's raw path. Tampermonkey follows those, not the catalogue, once a script is installed.
4. Add its entry to `modules-unstable/modules.json` with the same `id` as the stable entry, `status: "unstable"`, and an `installUrl` under `modules-unstable/`.

`node scripts/check-versions.mjs` enforces all of it: each file is checked against the catalogue for the folder it lives in, a copy here must be strictly ahead of what stable ships, the two URLs must point at the folder the file is actually in, and an entry whose file has gone is reported rather than ignored.

## Promotion

Only the repo owner decides when something is promoted, and they say so in those words. The six steps — copy up, rewrite the URLs, bump the patch once more, update `catalogue/modules.json`, delete the file, entry and section from here, re-run the checks — are in [ADR-0014](../docs/adr/0014-unstable-first-releases.md#promoting).

The extra patch bump at promotion is not ceremony. A tester's installed copy points at a `modules-unstable/` URL that promotion deletes; shipping stable on the same number would leave them there silently, updating from a 404 forever. One more bump makes the Manager offer them the stable file instead.

### `Lectio-Chairs-Up.user.js`
Stable `1.1.1` with a safety net around its background fetches (issue #36): an eight-second `AbortController` timeout on every request, an abort of anything in flight on `pagehide`, a jittered first request, a backoff that doubles from two seconds to a one-minute ceiling after three consecutive failures and clears on the first success, and one request at a time instead of a `Promise.all()` burst, so a request never starts while another is in flight. The ~30-day room-id cache and its expiry are untouched.

`1.2.0` also reports to the Manager's problem log (issue #24): if a timetable page has rendered `.s2skemabrik` blocks and none of them matches `a.s2skemabrik.s2brik[data-tooltip]`, it says so. Marking nothing on a day off and marking nothing because Lectio renamed a class look identical on screen, and this separates them.

`1.2.1` fixes the back/forward cache (issue #41). The `pagehide` listener the safety net shipped with was `{ once: true }` and set a flag that gated every fetch, so a page restored from the bfcache — which is never re-executed — came back with the flag still set and the listener already spent, and skipped every remaining request for the rest of that page's life, silently. It is now a normal listener split on `event.persisted`, paired with a `pageshow` that lifts the gate when the page really was restored; a page that is genuinely going away is marked gone and nothing brings it back. Stable `1.1.1` never had this, so there is nothing to hotfix for stable users.

`1.3.0` prunes its own caches on load and declares them (issue #29). The ~30-day room map was only ever checked for age on the one read path that looked at it, and the room-week cache had no expiry at all: one key per room per week, kept for as long as the browser profile. Both are now cleared as the page loads — the room map when it is past its life, room-weeks once the week is behind us. Both are declared to the Manager as prunable caches, so the storage readout can show their size and offer to clear them; the settings blob is declared and deliberately not prunable. A failed write reports `storage-write` once per page load instead of being swallowed.

`1.4.0` asks the Manager for a turn before each background request (issue #40). The start jitter keeps this module out of step with other copies of itself; a turn keeps it out of step with the other three modules, which is the part no module can arrange alone because it may not know they exist. It fails open on this module's own clock, which is the whole of it: no answer within 1.2s means no Manager, an old Manager or one that has stopped - the same case, and it means go - and a request the Manager acknowledged waits at most 8s more before going anyway and handing the turn straight back. That 1.2s is paid once per page view, not once per request: a request that goes unanswered is remembered, and the next one does not wait at all until something answers again. Nothing the Manager sends can make it wait longer. See [`docs/manager-request-slots.md`](../docs/manager-request-slots.md).

`1.4.1` moves the three notice-watcher `let`s (`noticeObserver`, `noticeFrame`, `noticeNeedsPlacement`) from the NOTICE WATCHERS block, far below the START block, up beside the rest of the notice layout state above it (issue #58). `main()` is called during the file's own evaluation, and a module-scope `let` declared after that call is in its temporal dead zone until evaluation reaches it - the shape that shipped three broken Manager versions. Nothing `main()` does synchronously reached these three, so nothing was broken; `scripts/check-boot-order.mjs` is deliberately blind to that distinction, and this copy now passes it instead of being listed as a deferred finding. No behaviour changes.

### `Lectio-Change-Radar.user.js`
An experimental timetable watcher — a compact themed radar HUD with urgency states, unseen-change tracking, configurable polling and a rotating local change log. Unstable-only so far; it has never had a stable release, so promoting it would be its first.

`0.6.2` finishes its background-fetch safety net (issue #39). The twenty-second `AbortController` timeout it already had is untouched; what is new is a random offset of up to four seconds on the first check of a page view, and a backoff that doubles from five minutes to a thirty-minute ceiling after two consecutive failed checks and clears on the first one that succeeds. The base and ceiling are the fastest and slowest cadences the Check-frequency setting offers, because a backoff shorter than the poll interval would be stepped straight over and one longer than half an hour would outlast the usefulness of the thing being watched. A tick still never stacks on a check in flight, and pressing Refresh or changing what is watched clears the backoff rather than being swallowed by it. Its `pagehide` teardown now suspends rather than switches off, so a page restored from the back/forward cache goes on checking instead of sitting there dead.

`0.7.0` also reports to the Manager's problem log (issue #24): a fetched week that rendered `.s2skemabrik` blocks none of which parsed is raised as drift, rather than being reported to the user as a week with no changes in it.

`0.7.1` closes the last gap in that safety net (issue #42): live `AbortController`s are now tracked in a Set and aborted when the page goes away, not only when the twenty-second timeout fires. It happens in `suspendPolling()`, which `pagehide` calls before it splits on `event.persisted`, so a page frozen for the back/forward cache stops holding a Lectio request open and still resumes checking on a persisted `pageshow`. The timeout itself is unchanged, and a controller is removed from the Set in the same `finally` that clears its timeout, so nothing accumulates.

`0.8.0` bounds the change log by bytes and drops dead identities (issue #29). The log was capped by entry count only, but a snapshot of every watched week sits in the same value, so what is written is now capped in characters as well, oldest log entries first — the state on screen is untouched, only what is stored is trimmed. Keys are scoped per Lectio identity, and a browser accumulated a whole snapshot for every identity it had ever seen; one that has not been polled in two months is now dropped whole on load. `0.9.2` reads the assignment list and the absence page it was always pointed at (issue #59). ### `Lectio-Theming.user.js`
Stable `0.18.0` with its storage declared to the Manager (issue #47). Two keys, and they are treated differently on purpose. `lectioTheming.background.v1` holds the re-encoded background picture - the single largest thing a person can be carrying in this site's 5 MB, up to two million characters - and is declared prunable as `state`: a Clear from the Manager's readout goes through `clearCustomBackground()`, the very same path as the module's own *Remove background picture* control, so the page repaints and re-announces exactly as if that button had been pressed. It is `state` rather than `setting` because a setting is never offered up for deletion, and this one is a file the person can pick again. `lectioTheming.settings.v2` is declared as a setting and is **not** prunable: the hand-built custom palette lives in it, and a key name gives nobody any way to know that. The prune listener matches on this module's id and the background key exactly; a request naming the settings key, or another module's key, removes nothing. A settings write that fails now reports `storage-write` once per page load. Nothing else about the module has changed - Stable `0.18.0` is frozen until the owner promotes.
